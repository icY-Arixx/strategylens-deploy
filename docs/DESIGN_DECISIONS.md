# StrategyLens｜产品设计决策

本轮整理于2026-10-28。按用户问题与取舍组织答辩材料，不表示所有外部调研在编码前发生。原始时间线见AI_DEV_LOG；证据级别见[竞品研究](COMPETITOR_RESEARCH.md)。用户明确确认的方向与AI提出、待人工确认的细节分开记录。下述后续验证均为计划，不能写成已完成用户测试。

## D01｜采用工作台而非聊天机器人

- 问题：多轮聊天容易掩盖“当前到底执行了哪些条件”。
- 备选方案：对话即答案；对话侧栏加股票卡；始终可见的条件与结果工作台。
- 最终选择：命令输入、紧凑条件、表格、证据抽屉；用户已确认工作台方向。
- 原因：把输入解释和可执行状态放在一起审查，支持横向研究与局部调整。
- 代价 / Trade-off：表达复杂意图时少了对话自由度，歧义需要专门的澄清交互。
- 后续验证：让用户复述当前执行条件，观察是否误将输入文本当作已执行规则。

## D02｜结果表格成为主视觉

- 问题：股票卡片不利于比较四项数值、缺失和多重失败。
- 备选方案：卡片列表；只显示入选结果；带固定金融列的三态表格。
- 最终选择：名称/代码、四指标、满足数、状态、主要原因的表格；用户已确认表格优先。四指标列固定保留为AI实现细节，待人工确认。
- 原因：对齐与tabular numerals减少跨股比较成本；删除某条件不应顺带隐藏已取得的金融值。
- 代价 / Trade-off：窄屏需要表内横向滚动，财务期和来源不适合全部铺在主表。
- 后续验证：1366/1440/1920布局与任务比较；再测用户能否识别最高波动和未知值，不能只看截图。

## D03｜Missing ≠ Fail

- 问题：null当0会制造假通过或假排除，失败调用与合法缺失也不是同一回事。
- 备选方案：补0；全部算Fail；Pass/Fail/Unknown并保存错误证据。
- 最终选择：三态；有Fail即Excluded，无Fail且有Unknown为Unknown；用户明确保留。
- 原因：结果必须忠实表达可判断性，未知不能伪装成金融事实。其他产品也有missing规范，非独家概念。
- 代价 / Trade-off：多一个结果集合，用户需要了解为何未被选中而又未被否定。
- 后续验证：null/0/失败+未知的强断言；任务中询问用户Unknown是否等于“不符合”。

## D04｜AI只产策略草稿或Patch

- 问题：语言模型容易把语义解释、金融事实与推荐结论混在一起。
- 备选方案：AI直接给股票；AI生成后自动取数；AI产草稿、程序校验执行。
- 最终选择：未来LLM仅编译草稿/局部Patch，程序处理Schema、冲突、数据、计算和裁决；用户编码前已明确原则。本轮仍无运行时LLM。
- 原因：可重放、可检查，金融判断由明确规则及证据决定。
- 代价 / Trade-off：指标白名单约束覆盖范围；模糊词需要显示假设而非装作唯一答案。
- 后续验证：Initial Compile与Patch的独立语义Eval，尤其明确数值优先与不支持指标处理；不以HTTP200作为成功。

## D05｜默认保留执行前的用户审查

- 问题：“估值合理”没有唯一PE阈值；自动执行会把假设误当用户意愿。
- 备选方案：输入后即执行；每次改动弹确认；可编辑条件后显式执行。
- 最终选择：生成草稿后用户审查，点击执行；编辑自动保存、旧结果立即stale。用户要求的生成→编辑→执行流程保留，不新增反复确认弹窗。
- 原因：把30倍这样的系统默认与用户明确输入区分，同时保持研究操作效率。
- 代价 / Trade-off：比直接给答案多一步；默认值仍可能产生锚定效应。
- 后续验证：能否找到来源说明并识别默认阈值；统计误执行、修改率和完成时间。

## D06｜What-if固定Snapshot

- 问题：条件和行情同时变化时，不能把候选变化都归因于修改。
- 备选方案：每次实时取数；只保存结果计数；保存不可变Snapshot并绑定revision。
- 最终选择：默认复用上次快照，显式刷新生成新ID；同ID才标条件归因。用户已确认。
- 原因：把“PE收紧”和“数据更新”分开，保留逐条件证据。
- 代价 / Trade-off：快照可能变旧；汇总as-of不是全市场原子切片，更不是PIT无前视数据仓库。
- 后续验证：同ID/不同ID即使值相同也区别提示；观察用户能否判断数据新鲜度与归因边界。

## D07｜自然语言修改采用局部Patch

- 问题：“估值严格一点，其他不变”不应意外改变盈利或风险条件。
- 备选方案：整策略重生；前端猜字段；按condition_id的显式Patch。
- 最终选择：未来Patch+base_revision+程序应用与校验；当前只有手动局部修改。用户确认差异方向，具体Patch Schema待人工确认。
- 原因：TradingView官方帮助明确新AI请求替换当前筛选状态，提示局部修改语义值得验证；不能由此声称其他所有产品没有Patch。
- 代价 / Trade-off：需要操作契约、歧义澄清、删除/多条件同指标的定位规则。
- 后续验证：“其他不变”的未触及字段完全一致率；遇多个PE条件必须明确目标或澄清。

## D08｜证据分层展示

- 问题：完整API字段对审计有用，却会淹没普通研究者。
- 备选方案：全部铺开；只给解释文案；人能理解的首层+完整证据折叠层。
- 最终选择：Drawer先展示实际值、执行阈值、三态、原因、来源和报告期；展开保留raw/normalized、request_id、时间、算法、复权等。用户已确认此方向，具体排版待人工确认。
- 原因：减少首屏负担，同时不删证据；主表汇总不替代逐条件检查。
- 代价 / Trade-off：折叠内容较难被发现，抽屉内长证据需要滚动。
- 后续验证：普通用户定位排除原因、审计用户定位request_id/null/算法，两类任务分开计时。

## D09｜已有成熟自然语言产品仍值得做什么

- 问题：问财、TradingView等已有自然语言入口与强大数据生态，小项目无法靠功能总量取胜。
- 备选方案：再做聊天选股助手；堆更多指标；聚焦可审查、双向证据和固定快照修改验证。
- 最终选择：可审计策略工作台；用户确认不以自然语言本身为核心差异。
- 原因：外部证据修正“透明条件/解释足够差异化”的假设；较完整的可归因研究闭环是可检验机会。公开资料未确认≠竞品不支持。
- 代价 / Trade-off：目标用户较窄；严谨性价值需任务证据，不能靠“首创”措辞替代。
- 后续验证：在四竞品中用同一组5任务做授权实测，对比条件理解、排除解释、局部修改和数据变化归因；本轮尚未执行。

## D10｜不扩展新闻/RAG/多Agent

- 问题：24小时题目容易被功能数量与技术框架带偏。
- 备选方案：扩新闻、回测、多Agent；先完成四条件可信筛选主链路。
- 最终选择：保留FastAPI+Domain+Adapter+SQLite+原生前端，禁止本轮额外范围；用户已明确确认。
- 原因：主要风险是线上数据未验证、语义误改与证据体验，这些不由多一个组件解决。
- 代价 / Trade-off：覆盖复杂研究问题有限，不能承诺完整投研平台。
- 后续验证：先完成真实单股probe，再根据实测权限/耗时决定全量；完成语义Eval后再评估扩展需求。

## D11｜真实/DEMO模式显式隔离

- 问题：线上失败时静默补Mock会制造假金融结果；大幅DEMO横幅又妨碍工作台使用。
- 备选方案：失败自动降级；整页演示说明；小而持续的模式标签+可打开的数据详情+结果范围说明。
- 最终选择：默认REAL；只有显式mock配置才用虚构10股。顶部徽标、表格范围与证据持续保留身份；用户确认真实性与界面收敛方向。
- 原因：模式可识别，失败不伪装成功；配置Key也不代表已成功验证。
- 代价 / Trade-off：缺Key时不能展示真实结果；需要单独DEMO环境验收UI。
- 后续验证：无Key时authentication_error、failed、无正常结果；仅离线fixture和DEMO通过不能写线上PASS。
